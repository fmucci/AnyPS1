# 23 — Keyboard layout file and mouse turning in the player (observed, second and third title)

The template player (`template/frontend/ps1_play.c`) reads its keyboard/mouse layout from a text file instead of fixed keys:

- `template/runtime/pad_input.h` (no SDL, unit-tested by `tests/runtime/test_pad_input.c`): the pad bit names (the bit map of `rt_pad_script_add`), the layout parser (`scheme wasd|classic`, `key <SDL name> <button>`, `key <name> = none`, `unbind`, `mouse on|off`, `sensitivity`, `mouse_left|right|middle <button>`) and the mouse generator.
- The player writes `input.cfg` with commented defaults on the first interactive start (not for scripted runs), loads it every start, logs lines it does not understand and unknown key names, and never lets Tab (fast-forward) be rebound. Package READMEs describe the file (`tools/package.py`).
- Default layout "wasd": W/A/S/D and arrows = d-pad, Q/E/F/Space = square/circle/triangle/cross (Z = cross, X = circle also work), 1/2/3/4 = R1/R2/L1/L2, Enter = start, Right Shift/Backspace = select. `scheme classic` is the earlier fixed layout.

## Mouse look (the pad is digital)
The BIOS pad word is 16 buttons: there is no analogue value to pass, so a mouse cannot drive a camera smoothly by itself. The player turns horizontal motion into left/right presses with a delta-sigma accumulator (one decision per virtual frame, 10 pixels per frame at sensitivity 1.0 keep a direction pressed every frame, clamped to 6 frames of backlog), which gives a duty cycle proportional to the motion; the game's own turn speed is the ceiling. F10 releases/captures the mouse (menus react to left/right), losing the window focus releases it, scripted runs and the `dummy` video driver never capture it. The recorded input (`--record`) is the final pad word, so mouse sessions replay identically.

## What a title still has to find out by itself (unknown until a person tries)
- What the game's buttons do (fire, action, strafe...): the defaults are conventions; the layout file lets a tester change them without a build.
- Whether turn speed is proportional to held time in that title, and whether a true free-look is possible: it needs the camera/heading variables (watch RAM while turning in a real gameplay moment: a hand-off test scene that is static changes nothing) and a host-side write; not part of the template.

## Mouse turns the player through the game's memory (observed in the second port, 2026-11-05; `LookProfile`)
Where a title's camera follows the player's heading, the mouse does better than pulses: `runtime/pad_input.h` has `LookProfile`/`padin_look_step` (pure, unit-tested on a fake RAM) and each title fills `runtime/look_profile.h` (the template ships it disabled, `enabled = 0`, and the mouse then turns by left/right presses). Sideways motion adds to the player's heading (a 10-bit angle in FB2) and the game's own camera follows; the player stands and turns on the spot. What the second port needed (finding 0052 of that port):
1. Find the camera function: log the first GTE rotation matrix loaded per rendered frame (`F2B_GTELOG=first-last`, build with `--calltrace`), `F2B_WATCH` the matrix struct to find its builder, read how the angle is made and what it follows (there: view target = orbit - heading).
2. The heading is a field of the player's object. Locate the object by looking for words that equal its address (`F2B_RAMBIN` dumps at several ticks); keep the three globals that always hold it. They are 0 before the player exists, which is how the host knows not to write during loading and menus. Do not use a "current object" global (it changes inside the update loop) nor a search by id and heading (ambiguous at level start, where both are 0).
3. Validate headless: `F2B_POKE_ADD=addr,width,delta,first,last`, `F2B_LOOK=first,last,dx,0`, screenshots with `--ppm-every`, RAM with `F2B_RAMBIN`. A replay of a person's session (`--replay`) gives a controllable gameplay moment; a static test scene does not respond to the pad. Never dump RAM through `F2B_DUMP` into a pipe/file without a cap (one run produced 127 GB of output).
Memory writes are not recorded by `--record`, so a session played this way does not replay from its `.rec` (use `mouse_mode turn`).
Alternative seen and dropped: an orbit offset the camera follows swings the view round the player without turning him, but in an aiming stance the view then leaves the aim, and the user of the second port wanted the player to turn with the camera.

## Walking relative to the camera without turning the player (2026-11-05, second port; `padin_walk`)
With the mouse turning the player, the keys should not turn him again. The game's d-pad is tank-style, but the second port's game has a side-step on L2/R2 (heading unchanged), "down" walks backwards facing front, and "up" together with L2/R2 only walks forward. `padin_walk(keys, tick)` maps W/S/A/D (and the arrows) to up/down/L2/R2 and makes a diagonal by alternating forward and side-step presses (6 of every 15 ticks forward, 9 side-step, about 49 degrees off forward there; measure it for a title: a forward press must last about 9 ticks to start walking, so other mixes were far from 45 degrees). No memory writes for the keys. Keys pass through as a plain d-pad while no trusted player exists or the mouse is released (F10), so menus work; a pause menu while the mouse is captured is not detected. Measuring recipe: hold one button over an idle player on a replay (`--press b@first-last` over `--replay`), read the player's position words from `F2B_RAMBIN` dumps, compare displacement vectors (finding 0052, addenda 4-5). A first try that set the player's heading and the camera offset together to face the walking direction was dropped: it worked but turned the player on every key press, which is confusing.

## Game controller sticks (2026-11-05, second port)
In camera mode the left stick goes through the same walking code as the keys (`padin_stick_dirs`: 40 % dead zone, 8-way) and the right stick x axis is mouse motion (`padin_stick_look`: 15 % dead zone, squared response, `stick_speed` pixels per frame at full deflection). `pad_r1` / `pad_r2` in `input.cfg` rebind what the right shoulder / trigger press (the second port: triangle = draw/aim, square = fire, like its mouse buttons). The d-pad stays raw. Unit-tested; not tried with a physical controller.
